# Задачи на будущее

Записано по итогам security-аудита (коммиты `6a6f830..ab6b27d`). Не делать «заодно» — каждая задача отдельная.

## Безопасность

### 1. Перепродажа последней единицы товара (средняя)
`OrderService.CreateOrderAsync` читает `Stock`, проверяет и уменьшает в памяти, `SaveChanges` пишет значение целиком.
Два параллельных заказа на последнюю единицу оба проходят проверку и оба оформляются (остаток уходит в минус).
**Что сделать:** атомарное условное списание на уровне БД (как уже сделано для счётчика промокода,
`PromoCodeRepository.TryIncrementUsageAsync`): `UPDATE ... SET Stock = Stock - @q WHERE Id = @id AND Stock >= @q`
в одной транзакции с созданием заказа, провал — «недостаточно на складе». Альтернатива: токен конкурентности
(`xmin`) на `Product` и повтор при `DbUpdateConcurrencyException`.
**Закрепить тестом:** N параллельных заказов на товар с остатком 1 — успешен ровно один.

### 2. Access-токен живёт до 15 минут после отзыва сессии (низкая)
В access-токене есть claim `sid` (id семейства сессии), но JwtBearer не проверяет, жива ли сессия.
Отозванное устройство (logout-all, отзыв админом, кража токена) может ходить с уже выданным access-токеном до его истечения.
**Что сделать:** в `JwtBearerEvents.OnTokenValidated` проверять, что семейство `sid` не отозвано, с кэшем 15–30 секунд
(`IMemoryCache`, чтобы не ходить в БД на каждый запрос). Компромисс: отзыв вступает в силу с задержкой до длительности кэша.

### 3. Подмена X-Forwarded-For и лимиты по IP (проверить на Railway)
`Program.cs` очищает `KnownProxies`/`KnownIPNetworks` и оставляет `ForwardLimit = 1`: лимиты (вход 10/мин,
регистрация 5/мин, общий 100/мин) считаются по «правому» адресу из `X-Forwarded-For`. Это безопасно, только если
прокси Railway всегда **добавляет** (или перезаписывает) реальный адрес клиента справа. Локально, без прокси, заголовок
подделывается свободно и обходит лимиты (так я и гонял проверки).
**Что сделать:** проверить настройку/поведение самого Railway (документация/дашборд, свой одиночный запрос к своему сервису),
а не массовыми тестовыми запросами к проду. Если прокси не гарантирует — доверять только известной подсети прокси.

## Остальное из аудита (по решению владельца)
- Регистрация на занятый e-mail отвечает 409 (перебор адресов). Скрывается только подтверждением по почте — почты в проекте нет.
- Лимит попыток на аккаунт (нарастающая задержка), помимо лимита по IP.
- Эндпоинт смены/сброса пароля, который вызывает `AuthService.LogoutAllAsync` (отзыв всех сессий) — сейчас смены пароля нет.
- Заголовки безопасности на фронтенд-хосте (HSTS, X-Frame-Options/frame-ancestors, Referrer-Policy): сейчас отдаётся только
  `x-content-type-options`; настраивается на стороне хостинга (например `Caddyfile`, если Railway его подхватывает).
- Перекодирование загруженных изображений (защита от полиглотов); хранилище загрузок на постоянном томе/S3.
