## 1. Общий контекст

Family Shop — интернет-магазин полного цикла для рынка Казахстана/СНГ: не только одежда (мужское/женское/детское), но и обувь и сумки, бытовая техника, спортивные товары, посуда, аксессуары. Заказчик смотрит в первую очередь на дизайн и фронтенд — это стабильный приоритет при любых компромиссах.

Репозиторий: github.com/Dodikhudoev-Ahmad/Family_Shop
Работа: chat.claude.ai — планирование и составление промптов; Claude Code (терминал VS Code) пишет реальный код. Крупные автономные задачи предпочтительнее мелких — экономят токены и время. Работай автономно, разумные дефолты — твоё решение, не жди подтверждения на каждый шаг, если задача не содержит явной развилки с необратимыми последствиями.

Прод:

- Backend: familyshop-production.up.railway.app

## 2. Стек

- **Frontend**: React + TypeScript + Vite
- **Backend**: ASP.NET Core + EF Core + PostgreSQL, Clean Architecture
- **Локальная БД**: PostgreSQL на нестандартном порту 5433 (Homebrew postgresql@16), НЕ 5432, как может быть указано в дефолтном appsettings.json. Роль `postgres` с паролем в user-secrets.
- Типичный симптом сбоя локального Postgres: мёртвый `postmaster.pid`. Чинится так: `rm /opt/homebrew/var/postgresql@16/postmaster.pid && brew services restart postgresql@16`

## 3. Архитектура backend (Clean Architecture, слой за слоем)

Backend разбит на 4 проекта, зависимости идут строго внутрь (Api → Application → Domain, Infrastructure → Application → Domain). Domain ничего не знает о внешних слоях.

### 3.1 FamilyShop.Domain
Ядро бизнес-логики, без зависимостей от EF Core, ASP.NET или чего-либо внешнего.
- **Entities**: Product, Category, User, Order, OrderItem, Review, PromoBanner, DataProtectionKey (для персистентных ключей шифрования сессий).
- **Value Objects**: Money (инкапсулирует цену + валюту, защищает от случайных float-ошибок), Email (валидация формата на уровне типа, а не строки).
- **Enums**: OrderStatus, ProductSortOrder, ProductSortBy, Gender (Мужское/Женское/Детское), PromoBannerPlacement, Role (в т.ч. Admin).
- **Result<T> паттерн**: методы сервисов возвращают Result<T> вместо исключений для ожидаемых бизнес-ошибок (например "товара недостаточно на складе"), что даёт контроллерам предсказуемый способ мапить ошибку в HTTP-статус без try/catch на каждом шагу.

### 3.2 FamilyShop.Application
Бизнес-правила и сценарии использования (use cases), не зависит от Infrastructure/Api напрямую — только через интерфейсы.
- **Services**: ProductService, CategoryService, OrderService, PromoBannerService и т.д. — оркестрируют бизнес-логику, вызывают репозитории через интерфейсы (IProductRepository и т.п.), не знают, что под капотом Postgres.
- **DTO**: ProductFilterDto и аналогичные — то, что реально приходит с фронта (страница, сортировка, диапазон цен, тип товара, размер) и уходит обратно клиенту, отделено от Entity, чтобы не утекали внутренние детали модели.
- **FluentValidation**: валидаторы для входных DTO (например заказ с двумя строками одного товара в разных размерах — валидатор должен пропускать дубль ProductId, если различается Size).
- Ключевой нюанс, который уже был найден и закреплён тестами: `DbSet.FindAsync` внутри цикла `CreateOrderAsync` возвращает **один и тот же трекнутый** объект Product для двух строк заказа с одинаковым ProductId (EF Core identity map) — поэтому списание/возврат остатка на складе автоматически суммируется корректно по всем размерам одного товара в одном заказе, переписывать эту логику заново не нужно, только закреплять тестами при доработках.

### 3.3 FamilyShop.Infrastructure
Реализация интерфейсов Application-слоя через конкретные технологии.
- **AppDbContext** (EF Core) — контекст Postgres, миграции лежат здесь же.
- **Repositories**: RepositoryBase<T> (generic CRUD), ProductRepository (GetByFilterAsync с пагинацией, сортировкой, фильтром по gender/category/price/search/productType), PromoBannerRepository (GetActiveAsync по Placement).
- **DataProtection keys персистентны через Postgres** — критично, чтобы сессии не сбрасывались при каждом деплое на Railway (при дефолтном in-memory хранилище ключей все залогиненные пользователи разлогинивались бы на каждом деплое).
- Идемпотентный **upsert-сидер**: при старте приложения проверяет наличие данных по стабильному ключу (Category — по Slug, Product — по CategoryId+Name) и либо обновляет существующую запись на месте (не трогая Id, чтобы не порвать связи с Order/Review), либо добавляет новую. Повторный запуск не создаёт дублей — это проверено многократными прогонами на реальной БД с существующими заказами.

### 3.4 FamilyShop.Api
Тонкий слой контроллеров + middleware, ничего не знает о деталях реализации.
- **Controllers**: ProductsController, CategoriesController, OrdersController, PromoBannersController, AuthController и т.д. — принимают запрос, вызывают Application-сервис, мапят Result<T> в HTTP-ответ.
- **Middleware**: ExceptionHandlingMiddleware (единая точка обработки необработанных исключений, логирует с полным stack trace; клиенту уходит только общее сообщение), rate limiting по IP (политики: вход/выход `auth` — **10/мин**, регистрация `auth-register` — 5/мин, `auth-refresh` — 20/мин, управление сессиями (`/auth/sessions`, `logout-all`) — без именной политики, только общий лимит, создание заказа — 10/мин, отзыв — 5/мин, проверка промокода — 15/мин, общий лимит — 100/мин; те же политики действуют и на мобильные эндпоинты, обойти их заголовком нельзя). Лимиты считаются по IP из `X-Forwarded-For` (`ForwardLimit = 1`): держатся на том, что прокси Railway добавляет реальный адрес клиента справа — проверка настройки на самом Railway вынесена в `TODO.md`.
- **Security** (после аудита безопасности):
  - **Пароли**: BCrypt (work factor 12). Политика на сервере: буквы + цифры, не длиннее 72 байт (bcrypt обрезает дальше), список частых паролей, не равен email. Вход с неизвестным email и с неверным паролем неотличим по ответу и по времени (dummy-verify).
  - **Access-токен**: JWT HS256 (алгоритм закреплён), 15 минут, с claim `sid` (id семейства сессии). При старте проверяется `Jwt:SecretKey`: ≥32 байт и без плейсхолдера `CHANGE_ME` вне Development, иначе API не запускается.
  - **Refresh-токены — семейства с ротацией** (таблица `RefreshTokens`, хранится только SHA-256): каждый обмен выдаёт новый токен той же семьи (`FamilyId`) и сразу гасит старый, ротация атомарна (одно условное UPDATE — из параллельных запросов успешен один). Повторное предъявление уже обменянного токена спустя 10 с (первые секунды — гонка двух вкладок) **отзывает всю семью**. Есть абсолютный предел жизни сессии: веб — idle 14 дней / абсолютный 60, мобильный — idle **7** дней / абсолютный 30. Не более 10 живых сессий на пользователя и тип клиента.
  - **Веб-контур** (`/api/v1/auth/*`): refresh-токен только в httpOnly cookie (`Path=/api/v1/auth`), в теле ответа его нет.
  - **Мобильный контур** `/api/v1/auth/mobile/{register,login,refresh,logout}`: refresh-токен в теле JSON, cookie не используются вообще; **device binding** — приложение шлёт `deviceId` (UUID из Keychain/Keystore), сервер хранит только его хеш; токен, предъявленный с другого устройства, отзывает сессию (запрос без корректного `deviceId` — 400 на валидации). Тип клиента определяет **маршрут и сохранённый тип токена**, а не заголовок: cookie-токен не подходит мобильному эндпоинту и наоборот (в обоих случаях сессия сжигается), заголовка `X-Client-Type` нет и доверять ему нельзя. Повторный вход с того же устройства заменяет прежнюю сессию.
  - **Отзыв сессий**: `GET /auth/sessions` (мои устройства, текущее помечено), `DELETE /auth/sessions/{id}` (чужой id — 404), `POST /auth/logout-all`, для админа `POST /admin/users/{id}/revoke-sessions`. Смены/сброса пароля пока нет; когда появится, она обязана вызывать `AuthService.LogoutAllAsync`. Access-токен переживает отзыв до 15 минут (см. `TODO.md`).
  - **CSRF**: cookie живёт с `SameSite=None`, поэтому `/auth/refresh` и `/auth/logout` защищены `CookieCsrfFilter`: обязателен заголовок `X-Requested-With: fetch` (фронтенд шлёт его в `api.ts`, без него — 403) и `Origin`, если он есть, должен быть из белого списка CORS. Остальные изменяющие запросы идут по `Authorization: Bearer` и CSRF не подвержены.
  - **Удаление аккаунта** (требование App Store 5.1.1(v)): `DELETE /api/v1/auth/me` с телом `{ password }`, под строгим лимитом входа (10/мин на IP), id берётся только из токена. Строка `Users` **не удаляется, а анонимизируется** (`User.Anonymize`: email `deleted-{id}@deleted.invalid`, имя «Удалённый пользователь», хеш пароля `!deleted`, `DeletedAt`) — так `Order` (FK Restrict) и `Review` (FK Cascade) остаются целыми и без привязки к человеку; у заказов стираются контактное имя, телефон, город и адрес. Все refresh-токены удаляются; access-токен удалённого аккаунта отклоняется сразу (`ActiveAccountTokenValidator` проверяет пользователя на каждом запросе). Неверный пароль — 400 (не 401, иначе клиент решит, что сессия умерла), администратор — 403 (удаляется только вручную). Пока у пользователя есть активный заказ (статус Created/Processing/Shipped, т.е. не «доставлен» и не «отменён») — 409 `active_orders`; проверяется только после пароля, ничего не меняется и сессии не отзываются. Вход под удалённым аккаунтом невозможен, старый email можно зарегистрировать заново. Миграция `AddUserDeletedAt` аддитивная и идемпотентная.
  - **Авторизация закрыта по умолчанию**: `FallbackPolicy` = `RequireAuthenticatedUser` для всех эндпоинтов (в т.ч. новых без атрибутов); публичные действия помечаются `[AllowAnonymous]` **на действии, не на контроллере** (на классе он перебил бы `[Authorize]` у действий), админские контроллеры — `[Authorize(Roles = "Admin")]`. Список анонимных действий и роль у всех `/admin/*` закреплены тестом на рефлексии (`EndpointAuthorizationTests`) — новый публичный эндпоинт придётся добавить в него осознанно.
  - **Валидация**: фильтры списков (`ProductFilterDto`, `ReviewFilterDto`, `OrderFilterDto`) валидируются в контроллерах (глобальный `ValidationFilter` видит только аргументы действий — раньше лимиты `pageSize` молча не работали). DTO с паролями/токенами не печатают их в `ToString`; токены и пароли не пишутся в логи и не попадают в URL; ответы `auth` — `Cache-Control: no-store`.
  - **Сидер**: пароль админа берётся из `Seed__AdminPassword` (`SEED_ADMIN_PASSWORD` тоже читается); вне Development без него админ не создаётся и пароль в лог не пишется. Демо-рецензенты создаются со случайным паролем, известный старый (`Seed123!`) заменяется при старте.
  - Остальное: CORS whitelist (без placeholder-доменов), HTTPS/HSTS и nosniff/X-Frame-Options/CSP/Referrer-Policy на ответах API, CSP фронтенда через meta-тег, секреты только через user-secrets в разработке / переменные окружения Railway в проде — никогда не в appsettings.json или в коде.
- Cookie: `SameSite=None` (не `Strict`) — потому что frontend и backend на разных доменах Railway; `Strict` ломал сессию при каждой перезагрузке. Риск этого компромисса закрыт `CookieCsrfFilter` (см. CSRF выше). Вернуть на `Strict` можно будет только после перехода на единый домен (api.домен + домен), тогда же решится и проблема с блокировкой cross-site cookie в Safari.

## 4. Каталог и данные

- 8 категорий верхнего уровня были: Женское/Мужское/Детское/Обувь и сумки/Бытовая техника/Спортивные товары/Посуда/Аксессуары — но категория "Обувь и сумки" была впоследствии расформирована: её товары распределены по Gender внутрь Женское/Мужское/Детское (миграция `MoveShoesBagsToGenderCategories`, UPDATE по CategoryId, без пересоздания записей).
- `Category.HasSizes` — управляет тем, показывается ли фильтр по размеру для категории (скрыт для не-одёжных категорий).
- Размерные сетки хранятся не на категории, а определяются по `ProductType`: одёжная сетка (S–4XL, без XS), взрослая обувная (36–40), детская обувная (26–35, отдельно от взрослой), сумки — без размеров.
- `Product.ProductType` — явно проставляется в сидере (не инференсом из названия для новых товаров, хотя изначально была автоклассификация по названию для старых 52 товаров).
- Чипсы/фильтр по типу внутри категории показываются только если товаров этого типа в категории ≥ `MIN_TYPE_ITEMS` (константа, сейчас 5) — типы с меньшим количеством скрываются из UI, но товары остаются доступны через "Все" и поиск.
- `Product.IsBestseller` — используется для бейджа "Хит продаж" и слайдера "Хиты" на главной.
- Товары без размеров (сумки, техника) фильтр размера не показывают.

### Изображения товаров
- Источник — **Pexels API** (ключ в user-secrets: `Pexels:ApiKey`, читается оттуда в терминале, никогда не выводится в чат и не пишется в код/репозиторий). Ключ регенерируется на pexels.com/api после каждого использования, если он проходил через чат/терминал в открытом виде.
- Каждое фото перед использованием **визуально проверяется**: соответствие полу/возрасту/типу товара (мужское — мужчина на фото, не женщина), отсутствие брендовых логотипов/монограмм (был случай с кроссовками с брендовым паттерном на подошве — заменено), для детских товаров — категорический запрет на людей/детей в кадре, только предметная съёмка.
- Если подходящих фото под лимиты/тематику нет (например Pexels почти пуст на предметную съёмку бытовой техники/спортинвентаря без людей в кадре) — не натягивать случайные lifestyle-фото ради галочки, а честно сообщить и предложить альтернативу (другой источник, заглушка, снижение целевого числа товаров в этом типе).

## 5. Корзина

- Позиция корзины идентифицируется составным ключом `productId + size` — один товар в разных размерах создаёт отдельные строки, у каждой своё количество, свой `+/−`, своё удаление.
- Лимит количества в UI считается **агрегированно по товару**, суммарно по всем его размерам, а не по одной строке — иначе можно было набрать больше реального остатка на складе, комбинируя размеры.
- Товары без размеров ведут себя как раньше — ключ просто `productId`.
- Персист — localStorage, с защитной миграцией старого/битого формата без потери данных.
- Бейдж на иконке корзины (хедер, таб-бар) = сумма quantity по всем строкам.
- Backend: заказ с двумя строками одного товара в разных размерах создаёт два отдельных OrderItem; списание и возврат остатка при отмене заказа корректно суммируются по товару (см. раздел 3.2 про identity map).

## 6. Мобильный header

- "Умный" header: скрывается при скролле вниз (после ~80px), мгновенно появляется при скролле вверх, вверху страницы всегда виден. Логика — в `HeaderVisibilityContext`, скролл-слушатель через `requestAnimationFrame` + `passive: true`, с deadzone (~32px) от точки последнего решения, а не от предыдущего сэмпла — иначе реальный wheel-скролл (который "доезжает" до цели с локальными откатами на 20-30px) дёргает хедер посреди жеста.
- Header и панель категорий двигаются как единый блок через общую sticky-обёртку (`.header-stack`), а не по отдельности — иначе рассинхрон.
- Круглые фото-иконки категорий были заменены на горизонтальный текстовый scroll с акцентным подчёркиванием активной категории — прежняя концепция себя не оправдала у заказчика.
- Открытые оверлеи (поиск, бургер, мегаменю) держат хедер видимым, не дают ему спрятаться.
- **Критичная причина бага "хедер не залипает"**: `overflow-x: hidden` на `html`/`body` превращает элемент в scroll-контейнер и ломает `position: sticky` у потомков. Использовать `overflow-x: clip` вместо `hidden` для защиты от горизонтального скролла — та же защита, без побочного эффекта на sticky.
- Sticky-элементы на страницах (боковая панель фильтров каталога, панель заказа в корзине) должны иметь offset, учитывающий высоту хедера, иначе заезжают под него при скрытии/появлении хедера.

## 7. Дизайн-система

- Цвета: фон `#FFFFFF` (светлая тема) / через `--color-bg` (тёмная), secondary `#F7F5F3`, текст `#1A1A1A`, secondary текст `#8A8A8A`, акцент терракота `#C17A54`.
- Логотип: вордмарк "FamilyShop", буквы F и S терракотовые, остальное — основной цвет темы.
- Референс структуры (не более): milanomoda.store — компактные карточки, минимализм. Explicitly rejected: Zara/Mango/Uniqlo/SSENSE как слишком generic.
- Эстетика: **dark luxury / premium e-commerce**, никогда не Instagram Stories, не кислотные цвета, не избыточная анимация.
- Mobile-first: 1 карточка товара в ряд на мобиле (не 2 — осознанное решение, смотрится дороже), 4 на десктопе.
- Hover-анимации везде, skeleton-загрузка, fade-in через IntersectionObserver — стандарт, не отступать. Никаких `alert()`/`confirm()` браузера.
- Новые акцентные цвета (бейджи статусов, "Хит продаж" и т.п.) — в рамках текущей тёмной палитры, отличимые от существующего бейджа скидки, но не ярко-красный/зелёный неон, который выбивался бы из общей эстетики.
- Splash-анимация при первом заходе за сессию ("FS" → "Family Shop", ~2.3с) — с уважением к `prefers-reduced-motion`.

## 8. Обязательные проверки на КАЖДУЮ верстку

- Ширины: 320px, 375px, 390px, 430px.
- Обе темы — светлая и тёмная.
- Без горизонтального overflow за пределами явных scroll-контейнеров.
- Touch-target минимум 44×44px.
- Учитывать safe-area (notch/home indicator).
- Desktop не должен ломаться от мобильных доработок, если задача явно не про десктоп.

## 9. Данные, миграции и безопасность прод-среды

- На проде реальные заказы (например FS-1, FS-2) и реальные отзывы — **любые изменения структуры каталога/категорий только через идемпотентные UPDATE-миграции**, никогда через пересоздание/удаление существующих Product/Order/Review/Category.
- Сидер обязан быть безопасен для повторного запуска: upsert по стабильному ключу, никогда не дублировать при повторном `dotnet run`/деплое.
- Прод-пароли (admin, demo-reviewer аккаунты) были сменены после утечки в чат в рамках аудита безопасности — при любой повторной утечке секрета через чат/терминал сразу инициировать его ротацию, не дожидаясь напоминания.
- Известные открытые вопросы инфраструктуры (актуальность проверять по обстоятельствам): свой домен не куплен (сайт на `*.up.railway.app`), `VITE_SITE_URL` не должен содержать завершающий `/`, `VITE_CONTACT_*`/`VITE_SOCIAL_*` управляют видимостью блока контактов в футере (пустая переменная = блок не показывается, не нужно подставлять заглушки), загруженные админом фото на файловой системе контейнера пропадают при следующем деплое (нужен Railway Volume или S3 для персистентности — если это станет задачей), гонка при заказе на последний экземпляр товара (нет токена конкурентности) не исправлена.

- Frontend: `tsc` чисто, все `vitest` проходят.
