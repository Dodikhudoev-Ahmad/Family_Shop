# Деньги, выручка, время

Источник: `Domain/ValueObjects/Money.cs`, `Application/Services/OrderService.cs`, `PromoCodePolicy.cs`, `Application/Common/StoreClock.cs`, `OrderRepository.GetStatsAsync`, `Application/Services/FinanceService.cs`.

## Валюта и тип

- Валюта: тенге, ₸ (показывается в UI и сообщениях; в БД и `Money` кода валюты нет, только число).
- `Money` — структура с одним полем `Amount` (decimal). Отрицательное значение — исключение. Операции: `+`, `* int`, сравнения.
- В БД: `decimal(18,2)` (цены товара, `DiscountPrice`, `TotalPrice`, `DiscountAmount`, `OrderItem.Price`).

## Цена заказа

1. Цена строки = `Product.EffectivePrice` (цена со скидкой, если она задана) на момент заказа; сохраняется в `OrderItem.Price`.
2. Подитог = сумма цена × количество.
3. Промокод (если есть) уменьшает подитог; `TotalPrice` — итог после скидки, `DiscountAmount` — размер скидки.
4. Доставка в расчёте не участвует (платы за доставку в коде нет).

## Промокоды (`PromoCodePolicy.Evaluate`, общая для предпросмотра и заказа)

Отказ, если: не активен; вне `ValidFrom..ValidUntil` (UTC); подитог < `MinOrderAmount`; `UsageCount >= UsageLimit`.
Скидка: процент — `Round(подитог × % / 100, 0, MidpointRounding.AwayFromZero)` (целые тенге), с потолком `MaxDiscountAmount`; фиксированная — `DiscountValue`. Скидка не больше подитога. Код приводится к верхнему регистру. Использование увеличивается условным UPDATE в транзакции заказа (откат вместе с заказом).

## Округление

Правило: процентная скидка округляется **до целых тенге к ближайшему, .5 вверх** — `Math.Round(x, 0, MidpointRounding.AwayFromZero)` (150,5 → 151; 150,4 → 150). Банковское округление (`ToEven`) не используется. Округляется только процентная скидка; потолок `MaxDiscountAmount` и ограничение «не больше подитога» применяются после округления. Фиксированная скидка, цены товаров и `TotalPrice` отдельно не округляются (при целых ценах и целой скидке итог целый). Предпросмотр промокода и заказ считают через один `PromoCodePolicy.Evaluate`, поэтому суммы совпадают. Округление в `Math.Round(..., 2)` для среднего рейтинга отзывов к деньгам не относится.

## Статистика админки (`/admin/orders/stats`)

| Карточка | Определение |
|---|---|
| Новых сегодня | заказы, **оформленные** за текущие сутки магазина (`Orders.CreatedAt` от местной полуночи, `StoreClock`), в любом статусе **кроме `Cancelled`**. Источник — `Orders`, не платежи |
| Доставлено сегодня (поле API `ordersToday`) | число доставленных заказов за текущие сутки магазина: платежи `Income` минус `Reversal` с датой «сегодня» (см. «Финансы») |
| Выручка сегодня | сумма тех же платежей: `Income` − `Reversal` за сегодня (целые тенге) |
| Всего заказов | все когда-либо оформленные, включая отменённые |
| Новых заказов | статус `Created` |

С 2026-10-04 (Фаза 14, п. 4) «Доставлено сегодня» (раньше «Заказов сегодня») и «Выручка сегодня» считаются **по платежам, а не по заказам**: деньги появляются, когда заказ перешёл в «Доставлен» (оплата при получении), а не когда его оформили. Раньше карточки считали заказы, созданные сегодня, в любом статусе кроме отменённого; теперь заказ «сегодня» — тот, что завершён сегодня. Отменённый заказ платежей не создаёт. Заказ, оформленный вчера и доставленный сегодня, попадает в сегодняшние цифры; оформленный сегодня и ещё не доставленный — нет. Карточка «Заказов сегодня» переименована в «Доставлено сегодня» (4b, 2026-10-04); имя поля API `ordersToday` не менялось, чтобы не ломать клиентов, новое поле — `newToday`. «Новых сегодня» не зависит от платежей: заказ, оформленный сегодня и ещё не доставленный, в ней есть; отменённый (в том числе отменённый сегодня же) — нет. Заказ в 00:30 по Алматы (19:30 UTC накануне) — сегодняшний, в 23:59:59 накануне — вчерашний.

## Часовой пояс

- Настройка `Store:TimeZone`, переменная `Store__TimeZone`, по умолчанию `Asia/Almaty` (UTC+5).
- `StoreClock`: границы «сегодня / неделя (с понедельника) / месяц» — местная полночь магазина, переведённая в UTC. В БД даты только в UTC.
- Фильтр дат на странице «Заказы»: «с» — начало местных суток, «по» — последний момент местного дня (день включён).
- Сервер отдаёт `storeTimeZone` в статистике; сайт показывает даты заказов в этом поясе.
- Новые периодические подсчёты берут границы из `StoreClock`, не из `DateTime.UtcNow.Date`.
- Неизвестный пояс в конфиге — ошибка запуска (кроме `Asia/Almaty` без tzdata: тогда фиксированные +05:00).

## Оплата

Платёжного шлюза нет. Единственный способ — оплата при получении. Деньги фиксирует модуль «Финансы» (ниже).

## Финансы (Фаза 14, п. 4)

Доступ — только `Admin`; роли «Бухгалтер» нет.

### Платежи (`Payments`)

- Два типа: **`Income`** (приход) и **`Reversal`** (сторно — возврат прихода).
- **Income** создаётся ровно один раз, в транзакции перехода заказа в `Delivered` («Завершён» в интерфейсе): сумма = `Order.TotalPrice`, округлённая до целых тенге (`Math.Round(x, 0, MidpointRounding.AwayFromZero)`, при целых ценах — без изменений), время = момент перехода (UTC). Заказ, итог которого округляется до 0 (промокод на 100 %), денег не принёс и `Income` не получает. Запись делается `INSERT ... ON CONFLICT DO NOTHING`; уникальный индекс `(OrderId, Type)` не даёт создать второй `Income` ни повторным запросом, ни гонкой.
- **Reversal** — запись на ту же сумму, что и `Income` заказа, создаётся, если **завершённый** заказ отменяется (`Delivered → Cancelled`). Защита в сервисе: сторно возможно только при существующем `Income`, не больше одного на заказ (тот же уникальный индекс), сумма берётся из `Income`, а не пересчитывается. **Сейчас переход `Delivered → Cancelled` запрещён** (`StateMachines.md`: `Delivered` финальный), поэтому сторно в рабочем потоке не возникает; логика заложена и покрыта тестами, а включится вместе с разрешением перехода (потребуется решить, что делать с остатком товара).
- Отмена до `Delivered` (`Created`, `Processing`, `Shipped` → `Cancelled`) платежей **не создаёт**: денег не было.
- Платежи не правятся и не удаляются; исправление только сторно.
- Сумма платежа всегда > 0 (проверка `CHECK` в БД); знак определяет тип.

### Расходы (`Expenses`)

- Вводятся вручную админом: категория (`Purchase` закупка, `Delivery` доставка, `Other` прочее), сумма, дата, комментарий (необязательный, ≤ 500), автор (id админа из токена).
- Сумма: **целое число тенге > 0** (не больше 1 000 000 000). Дробные суммы отклоняются (400).
- Дата — календарный день магазина (формат `yyyy-MM-dd`), не позже сегодняшнего дня магазина; в БД хранится как UTC-момент начала этого дня в поясе магазина (`StoreClock.StartOfLocalDayUtc`), как и все даты.
- Расход можно **удалить** (мягко, 4b); **редактирования нет**: ошибка исправляется удалением и новым расходом.
- **Мягкое удаление:** запись не стирается, у неё `IsDeleted = true`, `DeletedAt` (UTC) и `DeletedByUserId` (админ из токена). Удалённый расход **не входит** в баланс, итоги периода, график и Excel. В журнале он скрыт по умолчанию; фильтр «Показывать удалённые» выводит его серым, с пометкой «Удалён» и без кнопки удаления.
- **Повторное удаление идемпотентно:** тот же запрос ещё раз — успех без ошибки, `DeletedAt` и `DeletedByUserId` остаются от первого удаления (условный `UPDATE ... WHERE IsDeleted = false`). Несуществующий id — 404. Одновременные удаления: проигравший получает тот же успех.
- Платежи удалять нельзя ни при каких условиях (журнал приходов append-only; исправление — только сторно).

### Баланс

`Баланс = Σ Income − Σ Reversal − Σ Expenses` за выбранный период (расходы — только не удалённые). Отдельно показываются все три слагаемых.

### Периоды

Границы — только через `StoreClock` (Asia/Almaty, UTC+5), не `DateTime.UtcNow.Date`:

| Период | С | По |
|---|---|---|
| `today` | начало сегодняшних суток магазина | сегодня |
| `week` | понедельник текущей недели | сегодня |
| `month` | первое число текущего месяца | сегодня |
| `custom` | `dateFrom` | `dateTo` (день включён: до последнего момента суток) |

Платежи входят в период по `CreatedAt` (момент оплаты), расходы — по дате расхода; в обоих случаях сравнение с UTC-границами, полученными из местных суток. Платёж в 00:30 по Алматы (19:30 UTC накануне) принадлежит новому местному дню. График «12 месяцев» — 12 календарных месяцев магазина, текущий последний; месяц платежа определяется по местному времени.

### Бэкфилл

При миграции для всех уже существующих заказов в статусе `Delivered` без `Income` создаётся `Income` (`INSERT ... SELECT ... ON CONFLICT (OrderId, Type) DO NOTHING`, повтор ничего не меняет). У заказа нет отметки времени доставки, поэтому дата такого платежа = `Orders.CreatedAt`; сумма — `TotalPrice`, округлённый до целых тенге. Отменённым и открытым заказам платежи не создаются. Это значит, что выручка по старым заказам попадёт в месяц оформления, а не доставки.

### Excel

Экспорт (`GET /admin/finance/export`) — книга `.xlsx`: лист «Журнал» (все записи периода) и лист «Итоги». Значения из пользовательского текста (комментарии, имена авторов) записываются как строки и не исполняются как формулы. Даты — в поясе магазина. Не более 20 000 строк за выгрузку.
